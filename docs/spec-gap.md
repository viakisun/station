## 2. 횡단(cross-cutting) 갭 — 화면보다 우선 정리 필요

1. **도메인 객체 미완성**: SSOT §3은 10개 표준 객체(Robot, Module, WorkSession, **Route**, Event,
   Incident, Firmware, TelemetryChannel, **CalibrationProfile**, **AuditPackage**)의 필수 필드를 정의.
   현재 domain은 화면이 쓰는 필드만 부분 보유. 누락 객체/필드: Route(waypoint_list, safety_zones,
   validation_state), Command(lifecycle), CalibrationProfile, AuditPackage(artifacts/score/approval),
   ErrorCodeMap, DeploymentPlan/RollbackPolicy, NotificationPolicy, MaintenanceTask 등.
2. **권한·역할 매트릭스 미구현** (§00-6): 6역할(현장 오퍼레이터/현장 관리자/유지보수/제조사 개발자/
   배포 관리자/시스템 관리자) × 조회/실행/승인. 현재 nav·액션에 역할 게이팅 없음.
3. **audit_log 모델 부재**: 거의 모든 화면이 "감사 로그 기록"을 전제하나 실제 로그 객체/뷰어 없음
   (C04-08, 공통 footer 링크만 존재).
4. **크로스 컨텍스트 유지** (§00, §01-2): "맵에서 선택한 robot_id가 장애/펌웨어/HMI 이동 후에도 유지"
   가 요구되나, 현재 console 내 드로어 한정. field(HMI/Telemetry)로 넘어가면 컨텍스트 소실.
5. **ID 규칙 검증기 부재** (§00-5): RBT-/MOD-/TCH-/WKS-/CAL-/AUD- 규칙은 데이터엔 있으나 생성/검증 유틸 없음.
6. **상태 색상 토큰 불일치(의도적)**: SSOT §4는 normal #2E7D32 / warning #F9A825 / critical #E65100 …
   를 지정하지만, 프로토타입 tokens.css는 더 절제된 값(--st-normal #3a7d4a 등)을 사용. "디자인 100% 보존"
   원칙상 프로토타입 값 유지. → 추후 정합 필요 시 결정 포인트.
7. **현장 디바이스 해상도**: SSOT는 HMI 1024×600/800×480, 태블릿 1024×768 기준. field 앱은 현재
   데스크톱 폭 기준 — 실제 해상도 프레임/터치영역(64px) 반영 필요.
8. **실시간 추상화**: 이벤트 스트림·OTA 진행·conformance 러너가 setInterval 가짜. SSOT는 Event Bus/
   MQTT/SSE 전제 → 실시간 데이터 소스 추상화 필요(Track C).

## 3. 핵심 사용자 흐름(미완) — 화면이 모여야 성립

SSOT가 명시한 폐루프 흐름 중 현재 "끊겨" 있는 것:

- **모듈 온보딩 폐루프** (C02): 온보딩→Capability→Protocol→Conformance→Audit→Registry 등록.
  현재 Conformance/Audit만 존재, 앞단(01~05)·SDK·이슈보드 없음.
- **펌웨어 폐루프** (C04): 등록(01)→분석(02)→호환성(03)→**승인(04)→배포계획(05)**→모니터(06)→
  **롤백(07)**. 승인·배포계획·롤백이 빠져 "분석→배포"가 연결 안 됨.
- **장애 폐루프** (C03→C04/H01): 이벤트→incident→**원인분류(04)**→조치(05)→**재발/포스트모템(10)**→
  펌웨어/파라미터 개선. 원인분류·재발분석 없음.
- **현장 작업 폐루프** (H01): 페어링→홈→**작업제어(02)**→**캘리브레이션(06/07)**→**점검/유지보수(10)**→
  **e-stop 복구(11)**. 현장 운영 본체가 거의 비어 있음.
- **Telemetry 폐루프** (T01): **온보딩(00)**→채널맵(02)→캘리브(03)→정책(06)→품질(08)→**Audit export(09)**.
  온보딩·export가 빠져 Audit/HMI 동기화 고리 미완.

## 4. 권장 진행 순서 (제안)

**Phase 0 — 스키마/공통(횡단 갭 1·2·3·5)**: 도메인 객체·필드 SSOT 정합화, 권한 매트릭스 모델,
audit_log 모델, ID 유틸. → 이후 모든 화면이 동일 기반 위에 올라감. **Track B(데이터 확장)와 합쳐 진행 권장.**

**Phase 1 — 폐루프 완성(가치 큰 순)**:
1. C04 승인(04)·배포계획(05)·롤백(07) → "분석→배포→롤백" 완성
2. C03 원인분류(04)·재발/포스트모템(10) → 장애 폐루프
3. H01 작업제어(02)·캘리브레이션 허브/단계(06/07)·e-stop(11) → 현장 운영 핵심
4. C02 온보딩(01)·Capability(02)·Protocol(03) → 모듈 온보딩 앞단

**Phase 2 — 보강 화면**: C01-02/03(맵·경로 디자이너, 대형), C01-08/09, T01-00/04/05/09,
C02-04/05/08/09/10, C03-06/07/09, C04-01/08/09/10, H01-03/04/05/08/09/10, T01-07/10.

**Phase 3 — 횡단 6·7·8**: 색상 토큰 정합(결정 필요), 현장 해상도/터치, 실시간 추상화(Track C).

## 5. Track B(데이터)와의 연결

미구현 화면 대부분은 **새 도메인 객체**를 요구한다(Route/Waypoint, CalibrationProfile, AuditPackage
artifacts, Command lifecycle, DeploymentPlan/RollbackPolicy, ErrorCodeMap, NotificationPolicy,
MaintenanceTask, audit_log…). 따라서 **Phase 0(스키마 정합) + Track B(시드 제너레이터로 볼륨 확대)를
함께** 진행하면 두 번 일하지 않는다. 데이터 제너레이터는 다중 사이트/온실, 로봇 수십대, 세션 수백,
시계열 telemetry, 장애 이력, 벤더/모듈/펌웨어/배포 이력을 결정론적 시드로 생성하도록 설계한다.
